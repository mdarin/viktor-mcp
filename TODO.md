## Доработки на очередь 2

Вот итоговый архитектурный концепт, объединяющий все наши наработки, включая полнотекстовый поиск ParadeDB, а также новые вводные по переходу на Vikunja API v2 и использованию Bot Users.

Архитектурный концепт: «Детерминированное процессное ядро для LLM-агентов»
1. Концепция и цель проекта
Перевод LLM-агентов из парадигмы «свободного чат-бота» в парадигму «детерминированного воркера». Система выступает в роли жесткого диспетчера (Gatekeeper), который инкапсулирует бизнес-правила (workflow) и предоставляет агентам (OpenCode, CrewAI) унифицированный, отказоустойчивый API через стандарт MCP (Model Context Protocol).

LLM изолирована от прямого изменения состояния системы. Она может лишь предлагать артефакты, которые проходят через «ворота» MCP-сервера, валидируются конечным автоматом (FSM) и объективными метриками.

2. Ключевые архитектурные паттерны
Толстый MCP-сервер (Smart Gatekeeper): Инструменты MCP содержат строгую логику FSM, а не просто проксируют CRUD-запросы к трекеру.
Идемпотентность: Все вызовы к MCP-серверу защищены от сетевых сбоев и повторных попыток агента (retry policy).
Контекстный бюджет: MCP отдает агенту только ту часть контекста, которая актуальна для текущего статуса задачи (экономия токенов, снижение галлюцинаций).
Разделение источников истины:
Процессы и статусы = Vikunja (через API v2) + PostgreSQL.
Код и артефакты = Git.
Семантические требования = Qdrant.
3. Компоненты системы
3.1. Уровень данных (Data Layer)
PostgreSQL (Основное хранилище и State Manager):
Выступает базой данных для Vikunja.
Обеспечивает конкурентный доступ нескольких агентов без race conditions (Pessimistic Locking через SELECT ... FOR UPDATE).
Использует колонки JSONB для хранения FSM-метаданных (ключи идемпотентности request_id, история переходов).
ParadeDB (Полнотекстовый поиск внутри PostgreSQL):
Расширение (на базе Tantivy/Rust) для Postgres, обеспечивающее сверхбыстрый лексический поиск (BM25) без необходимости разворачивать Elasticsearch.
Роль: Позволяет MCP-серверу предоставить агенту инструмент search_history(keyword) для точного поиска кодов ошибок, названий переменных или ID задач (объединяя FSM-статусы и текст в одном SQL-запросе).
Git-интеграция:
Каждая задача — изолированная ветка (task/{id}).
Qdrant (Векторная БД):
Хранит векторизованные «семантические якоря» (бизнес-требования) для автоматической проверки на семантический дрейф (гибридный поиск в связке с ParadeDB: смысл + точные совпадения).
3.2. Уровень трекинга и управления (Vikunja Core)
Vikunja API v2:
Единственный интерфейс взаимодействия MCP-сервера с трекером. Гарантирует работу с современной, поддерживаемой маршрутизацией и более высокой производительностью по сравнению с v1.
Bot Users (Ролевая модель агентов):
Каждый LLM-агент (OpenCode, CrewAI) заводится в Vikunja как специальный Bot User (а не обычный пользователь).
Преимущества интеграции: Изолированные API-токены (без истечения срока действия), четкий аудит-трейл (в логах видно, какой именно агент изменил задачу), возможность гранулярной настройки прав (RBAC) и отвязка активности агентов от метрик живых людей.
3.3. Уровень бизнес-логики (MCP-сервер на Go/Rust)
Шлюз, реализующий интерфейс MCP. Включает модули:

FSM Controller (Конечный автомат): Блокирует недопустимые действия агентов.
Idempotency Manager: Предотвращает дублирование действий при таймаутах.
Инструменты (Tools API):
claim_task(task_id) — атомарный захват задачи от имени Bot User.
get_task_context(task_id) — умная выдача контекста.
search_history(query) — лексический поиск через ParadeDB.
submit_for_review(task_id, commit_hash) — смена статуса с Git-валидацией.
3.4. Фоновые процессы (Background Workers)
Semantic Verifier (Верификатор): Асинхронно забирает git diff при ревью, сравнивает с Qdrant-якорями. При дрейфе смысла — создает Shadow Task (Коррекция).
Watchdog (Сторожевой таймер): Периодически сканирует updated_at зависших задач и переводит их в stalled.
4. Жизненный цикл задачи (Workflow)
Init: Внешняя система создает задачу (Backlog) и генерирует якоря в Qdrant.
Claim: Агент (под аккаунтом Bot User) запрашивает задачу. БД блокирует запись, статус -> in_progress.
Work: Агент пишет код в ветку task/{id}, при необходимости использует search_history (ParadeDB) для поиска прецедентов.
Submit: Агент вызывает submit_for_review. MCP через API v2 меняет статус (после проверки Git).
Verify: Запускается фоновый Верификатор (оценка дрейфа). Провал проверки блокирует задачу для оператора.
5. Вне скоупа текущего этапа
Разработка UI (VSCode-плагины, Tray Apps).
Middleware для оператора (реагирование на заблокированные задачи).
