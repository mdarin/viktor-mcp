# ADR 0004: Контракт взаимодействия с трекером (статусы vs FSM-метаданные)

Статус: принято (2026-10-21)

## Контекст

Концепт «Очереди 2» (см. TODO.md) требует детерминированного
gatekeeper'а: FSM-модель статусов (агент не может перевести задачу в
запрещённое состояние) и идемпотентность повторов агентов. В концепте
есть противоречие: «единственный интерфейс — Vikunja API v2»
одновременно с «Pessimistic Locking через SELECT ... FOR UPDATE на
PostgreSQL» (то есть прямая работа со схемой БД Vikunja).

Спайки (карточки #609, #610) зафиксировали факты:

- API v2 — целевой интерфейс upstream: появился в Vikunja 2.4.0,
  `/api/v1` заморожен (только багфиксы и порты в v2). Live-проверка на
  v2.6.0: v2 работает с существующими API-токенами, конверт списков
  `Paginated{items, total}`, OpenAPI-схемы. Bot Users доступны только
  через v2 и только с Vikunja ≥ 2.7.0.
  Live-проверка на v2.7.1: поведение v2 без изменений.
- Схема БД Vikunja — внутренняя деталь реализации, не контракт:
  зависеть от неё означает ломаться при каждом апгрейде трекера.
- Vikunja API не даёт условных обновлений (нет compare-and-swap):
  атомарный claim «прочитал → проверил → записал» через API имеет
  окно гонки между агентами.

Ограничения проекта (ADR 0002, Makefile): один статический бинарник
без внешних рантайм-зависимостей; конфиг — локальные файлы; уже
используется XDG_STATE_HOME для shadow queue и sync state памяти.

## Решение

**Разделить источники истины по типу данных:**

1. **Статусы и содержимое задач — Vikunja, через API.** Единственный
   интерфейс к трекеру — HTTP API: `/api/v1` сейчас, `/api/v2` после
   миграции (карточка «Миграция internal/client с /api/v1 на
   /api/v2»). Никаких прямых запросов в БД Vikunja.

2. **FSM- и идемпотентность-метаданные — встроенный SQLite внутри
   viktor** (пакет `internal/fsmstate`, драйвер `modernc.org/sqlite` —
   pure Go, без cgo, статический бинарник сохраняется). Файл
   состояния — `<XDG_STATE_HOME>/viktor/fsm/<instance>.db`, по образцу
   shadow queue и memory state.

   Gatekeeper — единственная точка входа агентов в трекер (это
   фундаментальное допущение концепта). Значит, он же — естественная
   точка сериализации: атомарность claim'а обеспечивается ограничением
   целостности SQLite (`UNIQUE` на активный claim задачи), а не
   блокировками в чужой БД. Запись в Vikunja (assignee, статус) —
   эффект после локальной фиксации решения; при сбое API — откат
   локального состояния (журнал переходов в той же БД).

3. **Идемпотентность:** таблица `request_id → результат вызова`.
   Повтор вызова с тем же `request_id` возвращает записанный результат
   без повторного эффекта. TTL записи — конфигурируемый.

### Схема (минимум)

```sql
CREATE TABLE task_claims (
    task_id    INTEGER PRIMARY KEY, -- один активный claim на задачу
    agent      TEXT NOT NULL,       -- bot/агент, взявший задачу
    state      TEXT NOT NULL,       -- claimed | submitted | ...
    request_id TEXT NOT NULL,
    claimed_at TEXT NOT NULL
);

CREATE TABLE idempotency (
    request_id TEXT PRIMARY KEY,
    tool       TEXT NOT NULL,
    result     TEXT NOT NULL,       -- сериализованный ответ
    created_at TEXT NOT NULL
);

CREATE TABLE transitions (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id    INTEGER NOT NULL,
    from_state TEXT, to_state TEXT NOT NULL,
    agent      TEXT NOT NULL, request_id TEXT NOT NULL,
    at         TEXT NOT NULL
);
```

### Отвергнутые варианты

- **C: прямая работа со схемой PostgreSQL Vikunja** (`SELECT ...
  FOR UPDATE` по JSONB-колонкам). Отвергнут: схема не контракт,
  ломается при апгрейдах; ломает изоляцию gatekeeper'а; требует
  сетевой доступ к боевой БД трекера из агентов-хостов.
- **B: внешний PostgreSQL для FSM-метаданных** (отдельная БД
  `viktor-state`). Отвергнут на текущем этапе: нарушает принцип
  «один бинарник, нулевой ops-след», добавляет деплой-зависимость
  ради данных, которые по природе — локальный журнал одного
  процесса. Ревизия возможна при горизонтальном масштабировании
  gatekeeper'а (несколько процессов viktor на один инстанс) — тогда
  SQLite заменяется на общий PostgreSQL без изменения контракта
  инструментов.
- **Идемпотентность через settings.json** (существующий KV-стор):
  нет транзакционности и ограничений целостности — недостаточно для
  claim'ов.

### Статусы FSM — где живут

Источники истинности по статусу задачи остаётся Vikunja (поле done,
buckets kanban). FSM-состояние в SQLite — **проекция и надстройка**
gatekeeper'а (матрица переходов, claim, журнал), а не вторая истина:
при расхождении побеждает Vikunja, расхождение чинится re-sync'ом
(аналогично ADR 0003: память — проекция, не источник).

### Связь с ParadeDB/поиском

PostgreSQL + ParadeDB из концепта нужен только для `search_history`
(BM25) на dev-стенде (карточка «infra: docker-compose dev-стенд») и
не участвует в FSM/идемпотентности вообще.

## Последствия

- +1 зависимость: `modernc.org/sqlite` (pure Go). Проверить вес
  бинарника; при недопустимом росте — пересмотр в пользу файлового
  журнала (fallback-план, слабее по атомарности).
- Agent'ы обязаны слать `request_id` в мутирующих вызовах FSM-инструментов;
  старые клиенты без `request_id` — не идемпотентны (совместимость:
  поле опционально, без него — прямое исполнение).
- Semver: новые инструменты (`claim_task`, `get_task_context`,
  `submit_for_review`) — Minor bump (см. ADR 0002).
- Гонка при записи assignee в Vikunja между двумя инстансами viktor
  на один инстанс трекера не закрывается (documented limitation до
  ревизии B).

## Открытые вопросы

- TTL idempotency-записей и политика чистки (cron в gatekeeper'е).
- Поведение при крэше между локальной фиксацией и эффектом в API
  (журнал transitions позволит доразрешить при старте; решить при
  реализации).
